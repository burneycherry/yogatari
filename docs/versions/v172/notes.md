# v172 リリースノート

## 変更点

### iOS：中断後のバックグラウンド再生をリロードなしで復旧
- 着信や他アプリの音声で読み上げが中断されると、以降iOSがこのページのバックグラウンド音声を拒否し、ページを再読み込みするまで正常化しなかった症状に対応。
- 実機ログにより、この拒否はJavaScriptから直接は観測できないことが判明した。`play()` はresolveし `play` / `playing` イベントも発火、`error` は出ず `readyState` は4、`AudioContext` も `running` のままで、**`currentTime` だけが進まなくなる**。
- `checkAudioProgress()` が2秒ごとに `gAudioEl` の再生位置を監視し、4秒以上進まない場合に `markAudioSessionLost()` でしおりを保存して停止する。▶押下時（ユーザー操作の内側）に `rebuildAudioElements()` が音声要素を作り直してオーディオセッションを取り直す。
- v171で実装した「`AudioContext.state` が `'interrupted'`」「`play()` 3連続失敗」を合図とするリロード復帰（`markBgSessionBroken()`）は、実機ログ上一度も発火しないことが確認されたため削除した。中断時の `AudioContext` の実測値は `'suspended'` であり `'interrupted'` ではなかった。これによりリロード後の自動再生経路も無くなり、自動再生は章末カウントダウンによる章間の自動進行のみとなった。
- 中断を検知した際のバッジ表示を「⚠ 中断 ▶で再開」とし、`_audioSessionLost` から導出することで以降の `setBadge(false)` でも消えず、▶を押すまで残るようにした。

### Android：バックグラウンド再生の停止を解消
- Google TTSモードで、画面消灯から15.5〜17.7秒で必ず停止する症状に対応。停止は常に新しい段落の開始時に起き、段落の途中では起きなかった。
- 原因はChromiumの仕様。`media/base/media_content_type.cc` の `kMinimumContentDurationSecs = 5` により、5秒以下の音声は `kTransient`（通知音と同じ一時音）に分類され完全なオーディオフォーカスが与えられない。本アプリは段落ごとに別の音声ファイルを再生するため段落ごとにフォーカス要求が発生し、5秒以下の段落が多いことでバックグラウンド再生権が維持されていなかった。
- 対策として `silentLoopEl` の音源を、MP3のデコードに失敗した環境でのみ実行時生成の6秒無音WAV（`silentWavSrc()` / `_silentMode`）へ切り替える。5秒を超えるためChromeが `kPersistent` と判定し、ページが完全なオーディオフォーカスを保持し続ける。WAVはPCMのためコーデックを要さず、`SILENT_MP3` のデータURIをデコードできないAndroid Chromeでも確実に鳴る。
- 判定はUA判定ではなくデコード失敗の検知で行うため、MP3が再生できるiOSは従来どおりMP3を使用し挙動は変わらない。
- 対策後、Androidで停止しなくなり章をまたぐ自動進行も動作した。あわせてChromeのメディア通知が表示されるようになった（`kPersistent` として認識された証拠）。
- `keepAudioSessionAlive()` が段落間を埋めるために `gAudioEl` へ `SILENT_MP3` を渡す処理は、デコードできないAndroidでは行わないよう `_silentMode !== 'mp3'` で抑止した。

### Android：読み上げの音声が鳴らない不具合を修正
- 設定タブの試聴ボタンでは音声が聞こえるのに、読み上げの再生ボタンでは進行するだけで無音になっていた。
- `unlockAudio()` が解除用の無音再生のために `volume = 0` にした後、復帰処理を `then()`（成功時）にのみ書いていたことが原因。`startPlay()` は `unlockAudio()` の直後に `stopGoogleAudioFull()` を呼ぶため解除用の `play()` は必ず中断され `AbortError` で終わり、`volume` が0のまま残っていた。`volume` はiOSでは読み取り専用で無視されるため、この不具合はiOSでは表面化しなかった。
- 復帰処理を `finally()` へ移動して修正した。

### ロック画面・通知からの再生／一時停止を修正
- 一時停止後、ロック画面の▶を押しても再生できなかった症状を両OSで修正。
- 原因は2点。(1) 一時停止時に無音ループを止めていなかったためページは音を出し続けている扱いとなり、プラットフォームはメディアセッションを再生中のままにしていた。ボタンは見た目が▶でも実体は一時停止のままで、押すと `pause` ハンドラが呼ばれていた。(2) 一時停止時に `stopGoogleAudioFull()` が `gAudioEl` の `src` を空にしており、セッションを保持している要素が空になることでiOSがNow Playingの対象から外していた。
- 一時停止では `stopGoogleAudio()` で要素を停止するのみとし読み込み済み音声を保持、あわせて `stopSilentAudio()` で無音ループも停止するようにした。再開時は従来どおり段落の先頭から読み直す。

### 無音ループのsrcクリアによる潜在不具合を修正
- `stopSilentAudio()` が `src` を空にしていたため、空srcの読み込みがページURLの読み込みとして失敗し、そのエラーが `startSilentAudio()` のデコード判定に届いて `_silentMode` を誤って切り替える状態になっていた（Chromiumで mp3 → wav への誤切替を再現）。スリープタイマー発動時などにiOS側の方式が入れ替わる可能性があったため、`src` のクリアを削除し `pause()` のみとした。

### デバッグモード（計測ログ）の追加
- 設定タブ最下部にON/OFFトグルを追加。既定はOFF。
- ONのときだけ音声要素の `play` / `pause` のラッパー・メディアイベントの購読・計測タイマーを生成するため、OFFの間は再生経路に計測処理が一切入らない。
- ONにするとトップバーのバージョン表記のタップで計測ログ画面を開閉できる（OFF時は無反応）。再生位置の進行、アプリ起点の操作（`G.play() APP` 等）とプラットフォーム起点のイベント（`G:pause` 等）の区別、Media Sessionの各ハンドラ呼び出しを記録し、コピー／クリアができる。
- iOS・Androidのバックグラウンド再生の原因特定はいずれもこのログによってのみ可能だったため、CLAUDE.mdに削除・簡略化の禁止を明記した。

### ヘルプ・設定タブの文言と書式の統一
- ヘルプ（？）の「新着話の自動検出」の説明をユーザー指定の内容へ差し替えた。
- ヘルプモーダル全体および設定タブ全体で、項目ごとに不統一だった太字・文字サイズの書式を統一した。
- Google TTS使用量が98%を超えた際の切替先表記を「Kyoko」から「端末内蔵音声」へ変更。KyokoはiOSの音声名であり、Androidでは実際の音声名と一致しないため。

## 調査結果（実装変更なし）

- **Web Speech APIのバックグラウンド再生**：実機ログにより、iOS・Androidいずれも不可であることを確定した。中断の有無は無関係で、画面を消した時点で停止する。iOSはエンジンが無言で凍結しフォアグラウンド復帰時に未読部分を破棄して `end` を発火する（イベントが飛ばないため検出不可）。Androidはバックグラウンド移行の約30ms後に `error: interrupted` で打ち切られるが、`utt.onerror` が `interrupted` を無視するため停止に気付けない（この無視は `SS.cancel()` でも同じエラーが出るため二重読み上げを防ぐ意図によるもので、変更していない）。Google TTSモードと異なり `<audio>` 要素が鳴っていないためオーディオセッションを保持する主体が存在せず、無音ループによる対策は原理的に効かない。復帰は `visibilitychange` ハンドラが担う。

## 未実装・対応予定なし

- Service Worker / オフライン対応: 引き続き対応予定なし
- SSMLポーズ最適化: 削除済み、復活予定なし
- Android での `rebuildAudioElements()` による復旧: Androidの停止はオーディオフォーカスの問題であり要素の問題ではないため効かない。v172の無音ループ対策により停止自体が起きなくなったため、復旧経路の追加対応は行わない
