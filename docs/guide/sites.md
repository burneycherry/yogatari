# テキスト処理・小説サイトパーサー（詳細）

> `CLAUDE.md` から参照される詳細資料。本文抽出・目次解析・`SITE_RULES`・サイト対応を変更する前に読むこと。
> 実機ログ・実HTMLで確認した事実を記録する。推測で書き換えないこと。

## テキスト処理

- `splitText(html)` → DOMノードをプレーンテキストセグメント（段落単位）に変換
  - **フィルター後に1段落も残らなかった場合に限り、フィルター前の行を返す安全弁がある。削除しないこと。** エブリスタの章扉ページは見出し1行のみで構成され、既定ONの `chaphead`（章・話タイトル行）に一致して全段落が消え、セグメント0件となり再生できなくなるため。影響は全行がフィルターに一致するページのみで、通常の話の省略挙動は変わらない
  - **本文から話タイトルを拾う処理（`_pendingEpTitle`）は先頭3行までに限定している。削除しないこと。** 本文の途中・末尾にある「第一話読んでくださりありがとうございます！」のようなあいさつ文が `^第[一二三…]+話` に一致し、サイト側が持つ正しい話タイトルを上書きしていたため
- `splitSentences(text)` → 日本語句読点（`。！？…」』`）で分割
- `domToText(node)` → インライン要素を考慮した再帰的DOM→テキスト変換

## 小説サイトパーサー

- `parseSyosetuToc(doc, url)` — 小説家になろう目次の解析
- `parseKakuyomuToc(doc, url)` — カクヨム目次の解析
- `inferTocUrl(url)` — サイト判定とTOC URL構築
- `toNovelId(url)` — URLから小説IDを抽出
- `kakuyomuApolloState(doc)` — 作品ページの `__NEXT_DATA__` から Apollo ストアを取り出す
- `kakuyomuTocFromState(state, baseUrl, workId)` — ストアから全話の目次を構築する
- `kakuyomuWorkIdOf(doc, pageUrl)` / `kakuyomuEpisodeUrl(doc, pageUrl, epId, workId)` — 作品IDと話URLの解決
- `kakuyomuTotalFromToc(html)` — 総話数の取得（章ごとの「N話」ラベルの合計、または「全N話」）
- `bkSetToc()` は既知の総話数を小さい値で上書きしない（目次が実際より少ない件数を返す場合があるため）

### SITE_RULES の仕様

サイトごとの抽出ルールは `SITE_RULES` 配列で定義する。`host` で照合し、本文は `body`、章間リンクは `next` / `prev` を使う。

- **`rule.body` のカンマ区切りは「優先順位リスト」として先頭から順に試す。** `querySelector()` にカンマ区切りをそのまま渡してはならない。**CSSセレクタのカンマ区切りは文書順で最初にマッチした要素を返す仕様であり、記述順は優先度にならない。** エブリスタでは本文 `.content` の親が `.body` であるため、そのまま渡すと常に `.body` が選ばれ、話タイトル（`h1.subject`）が本文の先頭に重複して混入する
- テキストが空の要素は採用しない。アルファポリスの `#novelBody` のように、実在するが中身が空の要素を避けるため
- `minText` は本文の最小文字数（既定30）。エブリスタは章扉の見出しが「序章」のように短いため 2 を指定している。下げるほど取得失敗の検知は粗くなるため、本文セレクタが具体的なサイトに限って使う

### 対応サイトの実測事項

- **エブリスタ（estar.jp）** — 本文は `.mainBody .content`。章扉ページには `.content` が無いため `.mainBody .body`（見出しのみ）へフォールバックする。作品タイトルはビューアページの `<title>`「`【本文】<作品名>｜<N>ページ - 小説投稿エブリスタ`」から抽出する。話数は `?page=` から読む（末尾が数字でないため既定の抽出では常に1話目になる）。新着話数は目次ページの「全NNエピソード」から取得する。**目次からの話選択には非対応**（目次解析はなろう・カクヨム専用）
- **カクヨム（kakuyomu.jp）** — 本文は `.p-novel__body`。以下はすべて実機のHTMLで確認した事実であり、推測で書き換えないこと。
  - **作品ページはリンクとしては開いている章の先頭7話分しか描画しない**（残りは「つづきを表示」で遅延読み込み）。ただし **`__NEXT_DATA__` の Apollo ストアには全話分**（実測138話）の `Episode:<id>`（`title` / `publishedAt` を持つ）が入っている。目次は `kakuyomuApolloState()` / `kakuyomuTocFromState()` でここから構築する
  - **並び順はストアのキー順ではなく参照リストから取る。** キー順の `TableOfContentsChapter` は章の表示順と一致しない。章の一覧 → 各章が参照する話、の順にたどること
  - `publishedAt` が未来の話は目次に載せない（公開予定のため読めない）
  - **話ページには `__NEXT_DATA__` が無い。** 目次は作品ページからしか取得できない。話ページが持つのは表示中の話と次話のリンクのみ
  - **作品IDはページ自身が名乗るもの**（`canonical` / `og:url` / 現在の話へのリンク）を使う（`kakuyomuWorkIdOf()`）。アドレス欄の作品IDに話IDを連結すると、IDがずれている場合に必ず404になる。次話・前話のURLはページ内のリンクをそのまま使い、無い場合のみ組み立てる（`kakuyomuEpisodeUrl()`）
  - **本文ページはCloudflare Workers経由では403（nginx）を返す。** ブラウザ相当のヘッダー・作品ページで取得したCookieの付与・再取得のいずれも無効であることを実証済み。Deno Deploy経由では取得できる
    - **ただし2026-09-21の再検証では、同じ本文ページをCloudflare Workers経由で `status: 200` / `attempts: 1`（再試行なしの一発成功）で取得できた。** 同日、公開プロキシの `api.allorigins.win` と `api.cors.lol` も同じ本文ページを取得できている。
    - このことから、上の403は**経路そのものに対する恒久的な拒否ではなく、カクヨム側のIP単位の制限が続いていた状態だった可能性がある**。ただし200の観測は1回のみで、403が再発しない保証はない。
    - **両方の記述を残す。403を見ても経路の問題と即断せず、時間をおいて再確認すること。**
  - 短時間に多数のアクセスを行うとIP単位で弾かれ、作品ページは通るのに本文ページだけ403になる状態が続く。`docs/guide/proxy.md` の「取得の制御」はこの対策
- **青空文庫（www.aozora.gr.jp）** — 本文は `.main_text`。**Shift_JISで配信される**（`docs/guide/proxy.md` 参照）。1作品1ファイルのため章間ナビゲーションは無い。本文ファイル（`/files/〜.html`）のURLを指定する。図書カードのページには本文が無い
- **アルファポリス — 非対応。** HTMLの取得自体は成功するが、本文コンテナ `<div id="novelBody">` は空で、本文はページ表示後にJavaScriptが別途取得して埋める構造のため静的HTMLからは得られない。1話がさらに18ページ程度に分割される。また `content-viewer.js` がコピー・選択・右クリックの禁止、フォーカス喪失時の本文非表示、スクリーンショット阻止といったコンテンツ保護を実装しており、**これを迂回する実装は行わない方針**
- **ハーメルン（syosetu.org） — 非対応。** プロキシ経由でページ自体には到達するが、返るのはCloudflareのチャレンジページで `tryProxy()` のブロック検出が働く。自前プロキシのホワイトリストにも追加していない
